# KoreanCodex 1.0.1 — 실제 적용·검증 결과

검증일: 2026-11-11, Windows 11 / Paper 26.3 build 238. 저장소의 1.0.0 소스·배포물을 먼저 읽었고 운영 서버에는 도감이 설치되지 않은 것을 확인했습니다. 기존 구현을 보완한 **1.0.1을 실제 서버에 적용하고 정상 실행 중**입니다.

## 변경 내용

- 기존 8개 분야·80종, UUID 영구 등록·12업적·확인창·실제 1개 소비·작은 속성 보너스를 유지했습니다.
- 일반 기준 항목이 없던 분야에도 실제 일반 항목을 두어 분야 내 고급 2배·희귀 4배·전설 8배가 직접 비교되도록 조정했습니다. 80개 ID는 유지합니다. 네더의 별·겉날개·네더라이트 주괴는 전설 8배, 드래곤 알은 제외합니다.
- 넉백 저항을 `%p`로 표시합니다. 모든 수집·업적을 합친 상한은 이동 3%, 채굴 6%, 체력 +2HP, 공격력 +0.5, 방어 +1, 공격 속도 2%, 넉백 저항 2%p, 행운 +0.5입니다.
- 플레이어 저장 표식이 DB에 없거나 다른 UUID의 거래를 가리키면 `marker_reviews`에 영구 확인 대기로 기록해 재소비를 차단합니다. 운영자 `표식해제`는 이력만 정리하며 아이템·등록·보상을 자동 지급하지 않습니다.
- DB 스키마 1→2 이전에서 기존 등록·업적·개인 효과 설정을 보존합니다. 확인 대기와 처리 중 기록을 운영자가 조회할 수 있고 운영 권한 거부를 한국어로 안내합니다.
- 설치기가 `ServerStop.cmd`와 검증 가능한 전체 백업을 먼저 실행하고 **도감 JAR 하나만** 추가/교체합니다. Windows용 원본 SQLite DLL과 라이선스를 남겨 JAR를 약 2.6MB로 줄였습니다.

## 실제 운영 서버

- 설치 전 `ServerStop.cmd`로 서버와 기존 백업 관리자를 정상 종료했습니다. 전체 백업 `tycoon-server-backups/전체서버-20261111-140110-222.zip`을 만들고 모든 항목의 SHA-256을 검증했습니다.
- 최초 도감 부팅 전에 **기존 서버 파일 620개가 백업과 바이트 단위 해시 일치**했습니다. 기존 13개 JAR·월드·플레이어·경제·직업·강화·집·땅·상점·임무 데이터와 관리자를 바꾸지 않았습니다. 새 JAR는 `KoreanCodex-1.0.1.jar` 하나입니다.
- 실제 백업을 **다른 폴더로 전체 복원하고 620개 파일 해시 일치**를 확인했습니다. 복원 대상에 둔 새 파일이 과거 복원에 섞이지 않는 것도 검사했습니다. 운영 서버 자체를 되돌린 것은 아닙니다.
- 실제 설치된 `paper-api-26.3.build.238-stable.jar`와 JDK **27.0.1.0.3**으로 컴파일했습니다. 도감 부팅과 SQLite 생성이 정상이며 API·MockBukkit·테스트 Probe 클래스는 생산 JAR에 포함하지 않았습니다. `build-info.json`에 API·소스·JAR 해시를 기록했습니다.
- 14:05:39 최초 정상 기동. 콘솔의 `/도감관리 백업`으로 14:07:04 일관된 도감 DB 스냅샷 생성 성공.
- 기존 `/백업 지금` 경로로 저장·정상 종료·차가운 스냅샷·별도 압축·재시작. **14:08:17 정상 기동, 14:08:18 백업 성공**. 새 예약 ZIP의 외부 SHA-256과 내부 도감 JAR·설정·DB 포함을 확인했고 SQLite `quick_check=ok`, 스키마 2를 확인했습니다.
- EssentialsX/Spawn `2.22.1-dev+28-f8724e2`, KoreanEconomy 2.0.1, KoreanMenu 2.0.0, GP·Prism·WorldGuard·QuickShop·Windows 관리자를 유지했습니다. 운영 서버의 인증 설정·RCON·메모리 설정을 바꾸지 않았습니다.

테스트 계정·도감 완성 기록·아이템·추가 권한을 운영 서버에 복사하지 않았습니다. 사용자 실제 계정으로 운영 서버 전체 플레이를 수행한 것은 아닙니다. 기존 설정의 Paper 최신 버전 알림·선택 프로파일러 제한·QuickShop 세금 계정 경고는 숨기지 않았으며, 도감 기동 오류는 확인되지 않았습니다.

## MockBukkit·실제 SQLite — 33개

MockBukkit `26.3:4.120.0`과 실제 Paper API·파일 SQLite를 사용했습니다. 카탈로그·희귀도·모든 부분 수집의 단조 증가/상한, 소비·취소·중복·특수 아이템·권한·장비/물약과 별도 속성 유지·체력 비회복·DB 이전·재시작·백업·미상 표식·운영자 정리를 검사했습니다.

`Player.saveData()`는 MockBukkit이 구현하지 않아 호출 횟수와 실패 주입을 하는 **테스트 대역**입니다. MockBukkit 기본 속성 표에서 누락된 채굴 속도는 해당 Mock의 실제 속성 인스턴스에 바닐라 기본값 1을 준비했습니다. 실제 NBT 저장 성공은 위 Paper 복사본 검사와 구분합니다.

이 모의 하네스는 **JDK 25.0.2에서 33개 통과**했습니다. JDK 27에서는 MockBukkit/ByteBuddy 플러그인 클래스 로딩이 `No jar file selected`로 실패해, 재현 도구가 검증된 JDK 25를 명시적으로 요구하도록 했습니다. 이를 실제 JDK 27 Paper 서버 실패로 계산하거나 테스트 통과로 표시하지 않았습니다. 생산 컴파일과 실제 Paper 28개 그룹은 설치된 JDK 27에서 별도로 확인했습니다.

## 재현과 남은 범위

Maven Central에서 `test-pom.xml` 의존성을 별도 `.build/codex-tools/deps`로 받고 다음을 실행합니다. 기존 1.0.0 JAR를 확인된 SQLite 의존성 원본으로 사용하고 플러그인 클래스는 전부 재컴파일합니다.

```powershell
mvn -f korean-codex/test-pom.xml dependency:copy-dependencies -DoutputDirectory="저장소절대경로\.build\codex-tools\deps"
python korean-codex/windows.py build --server "서버폴더" --jdk "JDK27폴더"
python korean-codex/windows.py test --server "서버폴더" --jdk "JDK25폴더"
python korean-codex/windows.py package --server "서버폴더" --jdk "JDK27폴더"
```

운영 서버에서는 runtimeTest를 실행하지 마세요. 복사본 전용 가드·로컬 포트·비공개 RCON 파일·테스트 계정/초기 상태가 필요합니다. 테스트의 `full`은 기본 0종부터, 이미 검증 중 저장한 항목을 이어가는 경우에만 확인한 시작 인덱스를 `CODEX_FULL_START`로 지정합니다. 최종 80종·12업적과 모든 상한을 다시 확인합니다.

남은 범위는 실제 운영 계정의 전체 플레이, 10명 장시간 동시 부하·서버 경제 밸런스, 전원 차단·디스크 전체 고장, 모든 타사 속성 플러그인 조합, 실제 이동 거리·전투 피해·채굴 틱 수의 장기 계측입니다. 아이템·플레이어 파일·SQLite를 하나의 원자적 거래로 보장하지 않습니다. 불확실한 등록은 확인 대기로 남기고 자동 재소비하지 않는 정책으로 처리합니다.

Paper 공식 [AttributeInstance API](https://jd.papermc.io/paper/26.3/org/bukkit/attribute/AttributeInstance.html)의 임시 수정자·키별 제거 계약을 확인했고 실제 build 238 바이너리로 컴파일·실행했습니다.
